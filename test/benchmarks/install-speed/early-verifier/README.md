# Optional early image-verifier activation

Status: an unmeasured fixture experiment. No speedup is claimed. This restores an opportunity for concurrency present in omacom/omarchy-iso PR #145 at `dbffaa6c65344d644627a023c28661e08382b8fa`; it does not remove verification or change the installed package set.

PR145 enables `omarchy-root-image-verify.service` from `multi-user.target.wants`. Its normal systemd dependencies place it after `sysinit.target` and `basic.target`, allowing image hashing to overlap later live boot and user configuration. The existing benchmark fixture installs the verifier and starts it from the tty1 preflight, after the live login has begun. Starting earlier may reduce the subsequent wait, but concurrent reads may also delay boot. Only a complete matched cold-install comparison can establish the effect.

## Activation order

Pass `--early-preflight` to the existing [initramfs builder](../boot-overlay/make-initramfs.py). It supports `control` and `candidate` modes; builder mode is rejected. The default remains unchanged, including generated bytes and manifest fields when this flag is absent.

The appended initramfs still copies its small payload into the writable live root before PID1 starts. Early mode additionally installs a normal-dependency `omarchy-benchmark-preflight.service` and a `getty@tty1.service` drop-in that requires and orders after it. The oneshot runs the selected preflight once, with a 300-second activation timeout and 30-second stop timeout. It retains successful state with `RemainAfterExit=yes`. It has no dependency on getty or completion of `multi-user.target`, avoiding a dependency cycle.

Use the existing [image candidate preflight](../image/candidate-preflight.sh), or the composed [fast-reboot preflight](../fast-reboot/candidate-preflight.sh), without modification. It mounts the supplementary medium read-only, verifies the tooling and installer archives, activates the pinned installer, and queues the original image verifier asynchronously. Getty waits for activation to finish; it does not wait for the verifier to finish. The original installer still waits for successful full-image SHA-256 verification and checks qcow2 structure before disk preparation.

The early tty1 wrapper checks the service is active, its `ExecMainStatus` is zero, and nonempty start/end markers and the correct completion-mode marker exist. It then executes the original entrypoint without calling preflight again. A failed or timed-out activation prevents autoinstall. A repeated activation attempt fails before invoking preflight. A bad image hash remains a failure at the original verification gate even when activation itself succeeded.

The original verifier's command, conditions, priority, size-based timeout, and wait-helper failure handling are unchanged. A second bind or a second verifier is not introduced. Full package inventory, installation reasons, package-file checks, identity checks, installed-root boot validation, and independent firmware reboot with media removed remain required.

## Building a separate fixture

Add `--early-preflight` to the existing candidate initramfs build command, retaining its selected preflight, payload, and any `--disable-package-prefetch` option. Give the result a new output filename. Create a separate matched control using `--mode control --early-preflight` and the normal empty control preflight. Keep source media, cache policy, VM hardware, and clock boundaries matched.

Early manifests contain `early_preflight: true` and hashes for the generated unit, drop-in, service script, and wrapper. Absence of that field denotes the original tty1 activation behavior. Native-driver selection and workflow changes are separate integration work; this helper does not launch an experiment.

Activation records `/run/omarchy-benchmark/early-preflight-started` and `early-preflight-finished`, each containing the live boot ID and guest uptime, plus the existing `preflight-complete` mode marker. It also emits two `OMARCHY_BENCHMARK_EARLY_PREFLIGHT` lines to the QEMU serial device when available, preserving start/end evidence in the existing `serial.log` without target-side writes. These are activation timestamps, not verifier completion times. The host's original monotonic VM-start-to-installed-readiness clock remains primary; all hashing still happens after that clock starts. Do not interpret firmware accounting retained across a warm reboot as elapsed time for the installed boot.

## Focused contracts

```sh
python3 test/benchmarks/install-speed/boot-overlay/contract-test.py
python3 test/benchmarks/install-speed/early-verifier/contract-test.py --iso-source /tmp/omarchy-iso-fast
```

The early contracts execute the actual generated service/wrapper, activation script, and pinned verification wait helper against tiny disposable files and stubbed privileged operations. They cover one activation/verifier, archive corruption, image corruption, missing or failed service evidence, incorrect completion markers, and refusal of repeated activation. They do not replace a real firmware-boot test or measure installation speed.
