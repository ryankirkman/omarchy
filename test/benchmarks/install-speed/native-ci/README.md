# Native KVM installation experiment

The branch-only workflow `.github/workflows/install-speed-kvm.yml` runs the existing full installation benchmark on the standard public `ubuntu-24.04` runner. It requires actual `KVM_CREATE_VM` success and stops if KVM or sufficient disk space is unavailable. It never selects paid, larger, self-hosted or software-emulated runners. This is an experimental benchmark, not a production ISO release.

The job checks out the triggering commit, downloads Omarchy 4.0.2 and verifies SHA256 `2ef8e624aa1bec7e277e28056b8535a6c9373ba48d7ede3f1a01cb6d2373cfb8`. It pins the cidata harness to `omacom-io/omarchy-iso@2673c613d9a71e23920e43fbb951238145e0f1e8` and the prebuilt image installer to PR #145 commit `dbffaa6c65344d644627a023c28661e08382b8fa`. Checkout and artifact actions are pinned to verified commit IDs too. Host package versions, runner image version and machine resources are retained.

A separate fresh calibration install supplies exact package versions and explicit/dependency reasons. The existing image builder then constructs the common Btrfs filesystem inside a disposable Arch live VM using only the official ISO's offline mirror. Native host `qemu-img` compresses it after the builder shuts down. The resulting supplementary ISO is verified byte for byte and attached identically to both treatments. The original ISO, package set, VM resources, QEMU I/O policy and direct-kernel boot mechanism stay matched.

`repeat-installs.py` runs three fresh pairs in AB, BA, AB order, one VM at a time, on the same runner. It first measures the unchanged pinned image installer, then a distinct candidate with upstream package prefetch disabled. The second variant uses the same verified image and another three fresh control/candidate pairs. A valid first comparison below 2× is retained and does not prevent the second experiment. Full root-image SHA256 verification stays enabled in both candidates. It requires clean shutdown, installed-disk boot, package-file checks, exact package versions/reasons and unique identities before sealing each sample. It removes each validated target disk after its evidence is preserved. The comparison's primary metric covers VM start through installed-root SSH with actual polling uncertainty; guest installer phases are a separate metric. Each comparison records its own conservative full-clock 2× gate. The overall driver exits 0 if either completed variant passes, and exits 2 if both completed comparisons miss it; other failures are not timing samples. The original comparison stays at `repetitions/comparison.json`, and the follow-up is `no-prefetch-repetitions/comparison.json`. Build time is outside the per-install clock, as with creating the official release ISO.

The job begins only with at least 28 GiB free. Peak storage is expected below approximately 24 GiB for this package snapshot: the 5.8 GiB official ISO, sparse raw build filesystem and compressed result coexist during compression; the raw is then removed before supplementary ISO creation; only one installed target exists during repetitions. This is a planning budget, not a measured bound or a guarantee from GitHub. If less than 30 GiB is free before dependencies are installed, the workflow removes only known unused SDK trees on GitHub's fresh disposable runner to create headroom. With sufficient space it avoids that unrelated deletion work; the first observed runner already had 86 GiB free, and unconditional cleanup cost approximately 69 seconds. This is CI preparation time, excluded from installation metrics. Never run that cleanup step on a workstation or self-hosted runner. Allocation and free-space evidence remain visible; ENOSPC invalidates a sample.

The upload directory contains a fixed whitelist of timing, manifests, public identity evidence, validation output, logs and screenshots, plus small image-build provenance. Private SSH keys, cidata images/configuration, target/build disks, NVRAM and ISO files stay in temporary work storage. Evidence uploads run even after failure and expire after seven days. Supervisor timeouts and interrupts terminate only their own process groups and preserve small failure evidence.

## Trigger and capability gates

Only pushes to `perf/install-speed-kvm` that touch the workflow or benchmark paths trigger the job, and the job requires the public `ryankirkman/omarchy` repository. The default branch is untouched. No workflow dispatch endpoint or new secret is required. A GitHub App push can trigger a workflow; this differs from a workflow's own `GITHUB_TOKEN`, which suppresses most recursive triggers. The linked app still needs the separate Workflows write permission to publish `.github/workflows` files.

Read-only checks on 2026-09-05 confirmed that Ryan's repository is public and the connected user has admin/push access. The repository had no workflows or Actions runs. The available connector exposes workflow logs/artifacts and reruns, but no dispatch or enable-workflow method. Its installation metadata does not establish Workflows write permission or whether repository Actions are enabled. Publishing the reviewed branch and observing the actual result resolves those remaining gates; no benchmark has run merely because this workflow exists.

GitHub's current documentation lists 4 CPUs, 16 GB RAM and 14 GB storage for public standard Ubuntu runners, supports Linux hardware acceleration, and makes standard runners free for public repositories. The driver probes actual KVM and additional free storage rather than assuming either from those specifications. See [hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [workflow triggering](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow), [manual-run default-branch requirement](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), and [GitHub App workflow permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

## Local checks

`python3 test/benchmarks/install-speed/native-ci/contract-test.py` checks timeout cleanup of a real child process, the small-evidence whitelist and the source pins. YAML parsing and Python compilation cover workflow and driver syntax. These checks do not establish KVM availability, a successful guest build or any install speedup; those require the real Actions run.
