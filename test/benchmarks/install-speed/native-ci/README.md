# Native KVM installation experiment

The branch-only workflow `.github/workflows/install-speed-kvm.yml` runs the existing full installation benchmark on the standard public `ubuntu-24.04` runner. It requires actual `KVM_CREATE_VM` success and stops if KVM or sufficient disk space is unavailable. It never selects paid, larger, self-hosted or software-emulated runners. This is an experimental benchmark, not a production ISO release. The [complete direct-write trial](https://github.com/ryankirkman/omarchy/actions/runs/34001279394) passed all six installations and ordinary second boots, but reached only 1.8983× under the conservative full-clock test. The subsequent [file-index and full-animation overlap trial](https://github.com/ryankirkman/omarchy/actions/runs/34005907730) also passed all six installs and second boots, reaching 2.07731× at the median and 1.99957× conservatively. The strict gate remains false. The currently selected workflow adds firewall scheduling and private read-only logging-helper changes; that new candidate has no native result yet. The earlier intermittent boot failure remains unexplained; live console and read-only rescue diagnostics remain enabled for any new failure.

The job checks out the triggering commit, downloads Omarchy 4.0.2 and verifies SHA256 `2ef8e624aa1bec7e277e28056b8535a6c9373ba48d7ede3f1a01cb6d2373cfb8`. It pins the cidata harness to `omacom-io/omarchy-iso@2673c613d9a71e23920e43fbb951238145e0f1e8` and the prebuilt image installer to PR #145 commit `dbffaa6c65344d644627a023c28661e08382b8fa`. Checkout and artifact actions are pinned to verified commit IDs too. Host package versions, runner image version and machine resources are retained.

A separate fresh calibration install supplies exact package versions and explicit/dependency reasons. The existing image builder then constructs the common Btrfs filesystem inside a disposable Arch live VM using only the official ISO's offline mirror. Native host `qemu-img` compresses it after the builder shuts down. The resulting supplementary ISO is verified byte for byte and attached identically to both treatments. The release content, package set, VM resources, QEMU I/O policy and selected boot mechanism stay matched. The workflow now selects normal firmware boot with verified cold source pages; the direct-kernel driver option remains available for diagnosis.

The complete performance driver supports four variants with the shared image-mount restore correction, package prefetch disabled and release-gated reboot: early image verification, early verification with direct target writes, direct writes with overlapping finalization work, and that overlap with additional firewall/logging optimizations. The explicit two-variant command below remains available. `repeat-installs.py` gives each requested variant three fresh control/candidate pairs in AB, BA, AB order, one VM at a time, on the same runner. All four can reuse the same verified root image and matched early-activation control fixture. A valid comparison below 2× is retained and does not prevent later requested variants from running. Full root-image SHA256 verification stays enabled in every candidate.

Each sample requires clean shutdown, installed-disk boot, package-file checks, exact package versions/reasons and unique identities before sealing. The runner removes each validated target disk after preserving its evidence. The primary metric covers VM start through installed-root SSH with actual polling uncertainty; guest installer phases are separate. Each comparison records its own conservative full-clock 2× gate. The driver exits 0 if any completed variant passes, and exits 2 if all requested comparisons complete but miss it; other failures are not timing samples. The four early variants retain separate comparison paths; the selected trial writes `no-prefetch-fast-reboot-early-verify-direct-restore-overlap-firewall-logging-repetitions/comparison.json`. The original variants remain selectable with their existing output directories. Build time is outside the per-install clock, as with creating the official release ISO.

The job begins only with at least 28 GiB free in the default direct-kernel mode. Firmware mode requires 44 GiB; selecting early verification adds 6 GiB per additional requested variant because immutable derived ISOs coexist. A two-variant performance trial therefore requires 50 GiB. The selected single-variant workflow retains the existing 50 GiB preparation budget. The driver checks its actual work filesystem before downloads, source checkouts or VM preparation and records `disk-budget.json`. Direct-mode peak storage is expected below approximately 24 GiB for this package snapshot: the 5.8 GiB official ISO, sparse raw build filesystem and compressed result coexist during compression; the raw is then removed before supplementary ISO creation; only one installed target exists during repetitions. Firmware fixtures need more space because several complete derived ISOs coexist. These are planning budgets, not measured bounds or guarantees from GitHub. The workflow can remove known unused SDK trees on GitHub's fresh disposable runner when its preparation threshold requires more headroom. With sufficient space it avoids that unrelated deletion work; the first observed runner already had 86 GiB free, and unconditional cleanup cost approximately 69 seconds. This is CI preparation time, excluded from installation metrics. Never run that cleanup step on a workstation or self-hosted runner. Allocation and free-space evidence remain visible; ENOSPC invalidates a sample.

The upload directory contains a fixed whitelist of timing, manifests, public identity evidence, validation output, logs and screenshots, plus small image-build provenance. Private SSH keys, cidata images/configuration, target/build disks, NVRAM and ISO files stay in temporary work storage. Evidence uploads run even after failure and expire after seven days. Supervisor timeouts and interrupts terminate only their own process groups and preserve small failure evidence.

The driver defaults to `--install-timeout 1800` for calibration and measured installations. The workflow explicitly selects `--install-timeout 600`; this limits failed-attempt waiting and does not make a timed-out installation valid. Failure evidence remains retained. Direct-kernel installs also allow 300 seconds for SSH after the installer hands off to the installed disk. Firmware installations have a separate positive `--standalone-reboot-timeout`, defaulting to 600 seconds. The workflow selects 180 seconds for that gate, shared by calibration, controls and candidates and recorded as `standalone_reboot_timeout_seconds` in `experiment.json`. A standalone timeout remains an invalid sample, retains failure evidence and proceeds to bounded read-only rescue without retrying the sample. The first installed-readiness timing boundary, image-build deadline and rescue deadline remain unchanged.

A failed calibration or retained failed control/candidate sample can trigger one bounded rescue attempt before the ephemeral runner disappears. The original supervisor and QEMU must have stopped first. Paired failures require matching series, plan, failure-record and manifest provenance; missing or changed evidence fails closed without searching for another disk. A fresh live ISO boot uses the existing builder overlay to disable autoinstall and authorize a new disposable public SSH key. The failed target is attached with QEMU `readonly=on` and serial `OMARCHY_RESCUE`; the guest independently checks the disk and all partitions are read-only before mounting Btrfs with `ro,rescue=nologreplay,subvolid=5,nosuid,nodev` and the EFI partition read-only. It never unlocks encryption, changes the failed installation or retries the failed sample.

The rescue retains bounded JSON diagnostics for boot configuration, enabled services, network configuration from an explicit non-secret field allowlist, SSH configuration and file permissions, public SSH fingerprints, redacted installation logs and persisted journal warnings/service entries. No private key contents, password database or raw NetworkManager profile is exported. Timeout screenshots and the last failed SSH probe are retained too. The rescue subprocess has a six-minute wall limit including preparing its initramfs; its KVM supervisor is capped at 270 seconds. Failure rescue is always excluded from timing comparisons and preserves the original installation failure even if rescue itself fails.

[Run 33991603136](https://github.com/ryankirkman/omarchy/actions/runs/33991603136) failed during initial calibration at the original 1,800-second deadline. An installed tty2 login prompt was visible, but SSH never became reachable. No image build or candidate measurements followed. [The original failure evidence](../results/kvm-attempts/33991603136/) does not identify the cause; the separate rescue mount failed before recovering network or service diagnostics. The corrected no-replay mount option improves rescue diagnostics and is not a demonstrated fix for absent SSH. Separately, [local smoke-02](../results/local-image-smoke-2026-09-05/) passed package-file and standalone boot gates after the image-mount correction. That software-emulated functional test is not a paired native speed result.

## Optional firmware boot fixture

`--boot-method direct` remains the default. `--boot-method firmware` repacks a separate copy of the verified release ISO for each control/candidate initramfs, preserving the original EFI and GRUB boot chain. The repacker verifies every release file and the embedded EFI image, allowing only the intended initramfs replacement and ISOLINUX's layout-dependent boot-info bytes. The native driver retains each derived ISO's complete manifest and repack log, records it in `experiment.json`, and reuses it only for that exact initramfs digest. ISO preparation stays outside installation timing.

Firmware calibration and measured installations receive the derived ISO and `--verify-standalone-reboot`; they receive no direct kernel, initrd or command-line override. The selected `--source-cache` policy applies to the actual derived ISO and attached supplemental media. The image builder and failure-rescue VM continue using the original release ISO and a direct builder initramfs, with autoinstall disabled.

The first installed SSH response retains the installation clock boundary. After collecting the normal installation evidence, the runner ejects the release and supplemental media, unplugs CIDATA and requires another installed-disk reboot in the same QEMU process. It verifies a changed boot ID, preserved root/identities and absence of installation media before marking the sample valid. This additional proof is outside the recorded installation time and cannot convert a failed installation into a timing sample. `standalone-reboot.json` and its public root/identity evidence remain in every accepted sample. A firmware calibration explicitly requires that successful proof before supplying packages to the image builder. Selecting this option does not change the workflow or an already-running experiment.

## Selecting confirmation trials

The driver defaults to `--source-cache conditioned --variants upstream-image image-no-package-prefetch`, retaining the initial experiment's behavior. A later confirmation can run only the best candidate with three new pairs:

```bash
python3 test/benchmarks/install-speed/native-ci/run-native-experiment.py \
  --repo "$GITHUB_WORKSPACE" --work "$BENCH_WORK" --evidence "$BENCH_EVIDENCE" \
  --source-cache cold --variants image-no-package-prefetch
```

Before downloads or VM installation work, cold mode runs `OMARCHY_REQUIRE_COLD_EVICTION=1 bash test/shell.d/iso-vm-source-cache-test.sh`. This requires a real positive warmed-file eviction result on the actual runner; unsupported or ineffective hosts fail immediately, retaining `cold-cache-preflight.log`. Cold mode is requested for calibration and timed installation VMs; the untimed image builder retains its default. The VM runner verifies all source hashes first, then uses Linux `fsync`, `posix_fadvise(DONTNEED)` and `mincore` to require zero resident pages for the official ISO, supplemental read-only media, kernel and initramfs before starting the host clock. It does not require root or global `drop_caches`. Unsupported files or incomplete eviction fail the run. Preserve the runner's actual eviction evidence; requesting this flag is not proof that eviction succeeded. This checks cold source pages on the hosted runner, not physical USB behavior or every cache layer.

Each variant keeps a separate comparison, all requested variants run even when an earlier valid comparison misses 2×, and invalid CLI configuration returns exit 1. Use a fresh work directory for every invocation. The complete two-variant performance trial uses the following explicit options; each variant gets three new alternating pairs and one verified image build is reused:

```bash
python3 test/benchmarks/install-speed/native-ci/run-native-experiment.py \
  --repo "$GITHUB_WORKSPACE" --work "$BENCH_WORK" --evidence "$BENCH_EVIDENCE" \
  --boot-method firmware --source-cache cold --install-timeout 600 --standalone-reboot-timeout 180 \

```

## Diagnosing installed boot stalls

`--diagnostic-calibrations N` selects a separate boot-diagnosis mode, with an integer count from 1 through 6. It requires firmware boot and cold source pages and runs only ordinary stock control installations through the existing calibration path. Each attempt receives a fresh target disk, NVRAM and unique `diagnostic-calibration-01` name, while reusing the unchanged control ISO. The normal installed SSH, package-file and standalone reboot gates remain required. Successful attempts retain their small evidence and reclaim disposable disk/credential files; the first failure stops the sequence, retains evidence and invokes the existing bounded read-only rescue without retrying the sample.

The driver returns before creating an image builder or running any comparison. `experiment.json` records `measurement_valid: false`, the boot-diagnosis purpose, requested count, status, completed names and any failed name. Exit 0 means all requested diagnostic boots passed; it never establishes a speedup. Without this option, the full benchmark retains its original calibration, builder and variant flow. For example:

```bash
python3 test/benchmarks/install-speed/native-ci/run-native-experiment.py \
  --repo "$GITHUB_WORKSPACE" --work "$BENCH_WORK" --evidence "$BENCH_EVIDENCE" \
  --boot-method firmware --source-cache cold --install-timeout 600 --standalone-reboot-timeout 180 \
  --diagnostic-calibrations 4
```

The small-evidence whitelist preserves `timeout-console.{log,json}` and `standalone-timeout-console.{log,json}` when post-failure console diagnostics are available. Those records cannot turn a failed installation into an accepted sample.

## Trigger and capability gates

Only pushes to `perf/install-speed-kvm` that touch the workflow or benchmark paths trigger the job, and the job requires the public `ryankirkman/omarchy` repository. The default branch is untouched. No workflow dispatch endpoint or new secret is required. A GitHub App push can trigger a workflow; this differs from a workflow's own `GITHUB_TOKEN`, which suppresses most recursive triggers. The linked app still needs the separate Workflows write permission to publish `.github/workflows` files.

Initial read-only checks on 2026-09-05 confirmed that Ryan's repository is public and the connected user has admin/push access. The repository initially had no workflows or Actions runs. The available connector exposes workflow logs/artifacts and reruns, but no dispatch or enable-workflow method. Its installation metadata did not establish Workflows write permission or whether repository Actions were enabled. Subsequent branch publication and actual native runs resolved those capability questions; their evidence is retained under [results/kvm-attempts/](../results/kvm-attempts/).

GitHub's current documentation lists 4 CPUs, 16 GB RAM and 14 GB storage for public standard Ubuntu runners, supports Linux hardware acceleration, and makes standard runners free for public repositories. The driver probes actual KVM and additional free storage rather than assuming either from those specifications. See [hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [workflow triggering](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow), [manual-run default-branch requirement](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), and [GitHub App workflow permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).
