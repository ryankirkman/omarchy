# Finish-step overlap proposal

This source audit does not add a payload, native variant, or workflow selection. The proposed optimization was not retained because its process and terminal handling cost was disproportionate to its unmeasured benefit.

The audited dashboard is [Omarchy ISO PR145 at `dbffaa6c65344d644627a023c28661e08382b8fa`](https://github.com/omacom-io/omarchy-iso/blob/dbffaa6c65344d644627a023c28661e08382b8fa/configs/airootfs/usr/local/bin/omarchy-install-dashboard), with SHA256 `4871faded220498542e1d01a0cbae3f98c21ea5b4eea6bab94fa9e62b415ad89`. After its installer child succeeds, the dashboard displays full progress for another configured 0.4 seconds, calls `release_target`, calls `warm_reboot_path`, renders the finish screen and complete logo animation, then retains the static finish frame for a configured second before an unattended reboot.

`release_target` invokes the shared helper to sync, disable target swap, recursively unmount the target, close its LUKS mappings if present, and sync again. The existing [fast-reboot payload](../fast-reboot/README.md) makes either failed sync abort release. The dashboard records a release failure in its own `TARGET_RELEASED` variable, withdraws the medium-removal offer, and uses a graceful guest reboot. This function must remain in the foreground shell so a subshell cannot discard its failure flag.

`warm_reboot_path` reads live binaries, their libraries and the logo, then dry-runs `ttfx --version`, `stty size` and `gum --version`. It does not write the installed target. These reads are a possible overlap with foreground target release, provided warming is joined before the unchanged `render_finish`. That renderer prints the medium-removal offer before it runs the animation, so starting the renderer before release completes would move the safety promise ahead of its gate. The full animation, canonical static logo, sync/unmount/security gates and all setup must remain inside installation timing.

There are no isolated measured spans for release, warming or the animation in the accepted native evidence. The configured animation timeout of eight seconds is a stuck-process cap, not an observed duration. A benefit from overlapping warming and release would be limited by their actual spans and could be reduced by I/O contention; this audit establishes no speed improvement.

An isolated prototype required about fifty added Bash lines for worker launch, a separate session, signal handling, joining and bounded process-group cleanup. Preserving the original `stty` dry run when `TTY_PATH=/dev/tty` would require additional descriptor handling: a new session has no controlling terminal. Temporary shell contracts checked ordering, release and warming failures, and termination of a worker with a TERM-ignoring descendant, but did not establish terminal equivalence or a speed benefit. The prototype and its temporary contracts were removed. Revisit this proposal only if measured finish-step spans justify a small implementation that preserves terminal behavior and cannot leave an orphan worker after parent interruption.
