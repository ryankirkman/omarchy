# Verified root image recovered from an interrupted disposable build

This is image-build correctness evidence, not an installation timing sample. The reusable image contains all 941 package versions and the same explicit/dependency reasons as the successful official Omarchy 4.0.2 calibration. The prebuilt Btrfs/qcow2 installation method belongs to upstream Omarchy ISO PR #145, pinned to `dbffaa6c65344d644627a023c28661e08382b8fa`.

The original software-emulated builder stopped before completion and its supervisor sessions were no longer available. Its dedicated raw disk was retained. A newly booted live VM first checked all Btrfs data checksums without writing the filesystem. Although `pacman -Q` listed 941 packages and `pacman -Qk` returned zero, the final three database records were incomplete: zbar, zoxide and zram-generator each reported zero files. The other 938 package file counts matched calibration. This is why the final comparison must compare per-package file counts as well as names, versions and Qk's exit status.

Recovery preserved those malformed records, checked the exact three official archive identities and file ownership, and reinstalled only those packages. All 941 database NAME/VERSION fields, canonical file lists/counts, MTREE bytes and INSTALL presence/bytes then matched the official archives. The native archive reader extracted leading package metadata directly from the ISO's squashfs without copying the squashfs or unpacking package payloads; it did not validate all package bodies.

The recovery replayed all 32 matching PostTransaction hooks from the complete original Install transaction, with correct ordering and NeedsTargets input. It retained upstream's five deferred boot-hook masks. Every replayed hook returned zero. Replaying the complete hooks was necessary because the interrupted transaction had not reached its post-transaction hook stage. The last package has no INSTALL scriptlet in the official archive.

Final Qk exposed a separate clean-builder defect: cleanup deleted package-owned log directories and `/etc/resolv.conf`. Published commit `65d0548fdfcaca2577f68393391ab2f01f0d7a4f` (local fix `bd08eb3`) preserves owned log paths, removes empty unowned builder journal directories, and restores the resolver's packaged factory default. The recovered image's four already-deleted paths were restored from their exact archives and tmpfiles policy was reapplied. All 941 package file counts and Qk then passed. SHA256 verification also passed for all 11,085 regular files in the final six packages, covering 89,621,120 bytes across the interruption boundary, with no exclusions.

The image has an empty machine ID, no private pacman keyring or SSH host keys, no builder journal ID directory, and the exact packaged default resolver contents. Its source subvolume was sealed read-only, Btrfs was shrunk to 6,174,015,488 bytes, and a second complete Btrfs data-checksum check passed. After clean VM shutdown, native QEMU compression, qcow2 integrity checking, and a comparison of the entire logical raw/qcow2 content passed. The final supplementary ISO's embedded image bytes and complete ISO digest were then verified.

The raw disk was reclaimed only after logical content comparison; the loose qcow2 was reclaimed only after validating its embedded ISO bytes. Both cleanup records are retained. The large disposable disks/media are not stored in Git. The original image build and this recovery are outside the installation timing window. A candidate must still complete a fresh installation, boot from its installed disk, and pass the comparison contract before any speedup is accepted.

`recovery-procedure.tar.gz` preserves the exact bounded recovery scripts and source checks. Its hard-coded disk UUID and paths describe this interrupted fixture; the normal builder remains fail-closed on any existing filesystem. `tail-repair-evidence.tar.gz` contains the malformed database records, archive identities and exact replacement paths. The original failed Qk output remains alongside the successful result. No VM private SSH key, CIDATA credentials, installed target disk or private package-signing key is included.

The supplementary source review in `identity-source-review.json` checked all 43 package INSTALL scripts and 47 tmpfiles configurations, with payload hashes tied to the official archives. It found no install/chroot writer for persistent random-seed or machine-info, and dbus tmpfiles normally links its identity to `/etc/machine-id`. This is source-level evidence: physical random-seed/machine-info absence and the dbus path type have not yet been observed. `inspect-sealed-source.sh` and `sealed-source-byte-range.json` prepare a read-only check in the existing smoke VM after its functional/timing gates; they do not record that check as completed.
